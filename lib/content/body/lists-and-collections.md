## 26.1 `List` with Static Rows

`List` is SwiftUI's scrollable, row-based container — for a small, fixed number of rows known at compile time, you can list them directly as children, exactly like a stack:

```swift
List {
    Text("Row One")
    Text("Row Two")
    Text("Row Three")
}
```

Unlike `VStack`, `List` automatically provides scrolling, standard row styling (dividers, insets, tap highlighting), and integrates with the swipe-action/selection/editing features covered throughout this section — it's purpose-built for row-based content, not a general-purpose vertical container.

---

## 26.2 `List` with `ForEach` over Data

For a dynamic, data-driven set of rows, `List` combines with `ForEach` (recall the general `ForEach` mechanics tie into `for-in`'s iteration model from section 2.6, applied here to view generation):

```swift
struct Task: Identifiable {
    let id = UUID()
    var title: String
}

struct TaskListView: View {
    let tasks: [Task]

    var body: some View {
        List {
            ForEach(tasks) { task in
                Text(task.title)
            }
        }
    }
}
```

`List(tasks) { task in Text(task.title) }` (without an explicit `ForEach`) is a shorthand for exactly this same pattern when the entire list consists of one dynamic data source — `ForEach` becomes necessary once you need to mix static rows, multiple data sources, or sections (26.4) within the same list.

---

## 26.3 `Identifiable` and Row Identity

`ForEach` (and `List`'s data-driven initializer) requires each element to be uniquely identifiable — either by conforming to `Identifiable` (recall section 7.10) or by explicitly specifying an `id:` key path — so SwiftUI can track which row is which across data changes, insertions, and removals.

```swift
struct Task: Identifiable {
    let id = UUID()   // conformance to Identifiable — ForEach(tasks) works directly
    var title: String
}

// Alternative: explicit id key path for a type that isn't Identifiable
ForEach(tasks, id: \.title) { task in
    Text(task.title)
}
```

This identity is what lets SwiftUI correctly animate insertions/removals/reorders (a row is understood as "the same row, moved," not "removed and a different one added") and correctly preserve each row's own `@State` (recall section 25.14's structural identity discussion, applied specifically to list rows) as the underlying data array changes.

---

## 26.4 List Sections, Headers, and Footers

`Section` groups related rows together with an optional header and/or footer, using the exact same `List { }` container:

```swift
List {
    Section("Fruits") {
        Text("Apple")
        Text("Banana")
    }
    Section {
        Text("Carrot")
        Text("Potato")
    } header: {
        Text("Vegetables")
    } footer: {
        Text("Locally sourced")
    }
}
```

The simple `Section("Title") { ... }` form covers the common case of a plain text header with no footer; the more verbose trailing-closure form (`header: { }`, `footer: { }`) is needed when the header/footer itself needs to be more than plain text (an icon, a button, custom styling).

---

## 26.5 List Styles

`.listStyle()` changes the overall visual presentation of a `List` — its background, spacing, and section appearance — without changing any of the list's actual content or data-driven behavior:

```swift
List { /* ... */ }
    .listStyle(.plain)          // minimal styling, no inset grouping
List { /* ... */ }
    .listStyle(.insetGrouped)    // the classic "Settings app" rounded, grouped card appearance
List { /* ... */ }
    .listStyle(.sidebar)         // styled for use in a NavigationSplitView's sidebar column
```

Choosing the right list style is largely a design decision matching the surrounding context — `.insetGrouped` for settings-style screens, `.plain` for simpler content-focused lists, `.sidebar` specifically when the list serves as navigation inside a split view (recall the preview of `NavigationSplitView` coming in section 27.6).

## 26.6 Swipe to Delete with `onDelete`

`.onDelete(perform:)`, attached to a `ForEach` inside a `List`, enables the standard swipe-to-delete gesture, providing you with the index set of rows the user swiped to remove:

```swift
struct TaskListView: View {
    @State private var tasks: [Task] = [/* ... */]

    var body: some View {
        List {
            ForEach(tasks) { task in
                Text(task.title)
            }
            .onDelete { indexSet in
                tasks.remove(atOffsets: indexSet)
            }
        }
    }
}
```

`onDelete` only works on rows generated by a `ForEach` (not on static rows placed directly in `List`), and the `IndexSet` it provides maps directly onto `Array.remove(atOffsets:)` — this is the standard, idiomatic pairing for implementing swipe-to-delete against an `@State` array backing a list.

---

## 26.7 Reordering with `onMove` and `EditButton`

`.onMove(perform:)` similarly enables drag-to-reorder, providing source and destination indices you apply to your backing array with `Array.move(fromOffsets:toOffset:)`:

```swift
List {
    ForEach(tasks) { task in
        Text(task.title)
    }
    .onDelete { tasks.remove(atOffsets: $0) }
    .onMove { source, destination in
        tasks.move(fromOffsets: source, toOffset: destination)
    }
}
.toolbar {
    EditButton()   // toggles the list into/out of edit mode, revealing delete/reorder controls
}
```

`EditButton` is a built-in, pre-styled toggle for entering/exiting the list's edit mode — without it (or an equivalent manual `.environment(\.editMode, ...)` toggle), `onMove`'s reorder handles and `onDelete`'s delete controls typically aren't visible until the list is explicitly placed into editing mode.

## 26.8 Custom Swipe Actions

Beyond the default `onDelete` gesture, `.swipeActions()` lets you define entirely custom swipe-revealed buttons — with distinct actions, colors, and icons, and independent control over the leading (left) versus trailing (right) swipe edges:

```swift
ForEach(tasks) { task in
    Text(task.title)
        .swipeActions(edge: .trailing) {
            Button(role: .destructive) {
                delete(task)
            } label: {
                Label("Delete", systemImage: "trash")
            }
            Button {
                archive(task)
            } label: {
                Label("Archive", systemImage: "archivebox")
            }
            .tint(.orange)
        }
        .swipeActions(edge: .leading) {
            Button {
                markAsFavorite(task)
            } label: {
                Label("Favorite", systemImage: "star")
            }
            .tint(.yellow)
        }
}
```

`Button(role: .destructive)` (tying back to the button roles covered fully in section 28.11) automatically gets the standard red destructive styling; other swipe buttons can have their color customized via `.tint()`, and multiple buttons per edge are supported, revealed together as the row is swiped further.

---

## 26.9 Row Separators and Insets

`.listRowSeparator()` and `.listRowInsets()` give per-row control over the thin divider line between rows and the internal padding within each row, respectively — useful for rows that need custom edge-to-edge content or a visually distinct separator treatment:

```swift
ForEach(tasks) { task in
    Text(task.title)
        .listRowSeparator(.hidden)                              // hides the divider below this specific row
        .listRowInsets(EdgeInsets(top: 8, leading: 0, bottom: 8, trailing: 0))   // custom padding, e.g. for edge-to-edge content
}

List { /* ... */ }
    .listRowSeparatorTint(.blue)   // customizes the separator's color across the whole list
```

These modifiers apply per-row (when attached inside a `ForEach`) or list-wide (when attached to the `List` itself) — a common combination is hiding separators and zeroing insets together to achieve a fully custom, edge-to-edge row appearance that doesn't look like a "traditional" list row at all.

## 26.10 Selection in Lists, Single and Multiple

`List` supports built-in selection tracking via a `selection:` binding — a single optional value for single-selection, or a `Set` for multiple selection, both integrating automatically with edit mode and (on iPad/macOS) with keyboard/trackpad multi-select gestures:

```swift
struct TaskListView: View {
    @State private var selectedTask: Task.ID?

    var body: some View {
        List(tasks, selection: $selectedTask) { task in
            Text(task.title)
        }
    }
}

struct MultiSelectView: View {
    @State private var selectedTasks: Set<Task.ID> = []

    var body: some View {
        List(tasks, selection: $selectedTasks) { task in
            Text(task.title)
        }
        .toolbar {
            EditButton()   // multi-selection typically also requires edit mode to be active
        }
    }
}
```

Selection is tracked by the elements' `id` (recall 26.3's `Identifiable` requirement) rather than the elements themselves, which is exactly why `selectedTask` is typed as `Task.ID?` rather than `Task?` — this keeps selection tracking stable even as the underlying `tasks` array is mutated, sorted, or filtered.

## 26.11 `.searchable()` and Search Scopes

`.searchable()` attaches a system search bar to a view (typically a `List` inside a `NavigationStack`), binding its text to a `@State` property you filter your data against, with optional **search scopes** letting users narrow the search category:

```swift
struct SearchableListView: View {
    @State private var searchText = ""
    @State private var scope: SearchScope = .all
    let tasks: [Task]

    enum SearchScope: String, CaseIterable {
        case all = "All", active = "Active", completed = "Completed"
    }

    var filteredTasks: [Task] {
        tasks.filter { searchText.isEmpty || $0.title.localizedCaseInsensitiveContains(searchText) }
    }

    var body: some View {
        NavigationStack {
            List(filteredTasks) { task in
                Text(task.title)
            }
            .searchable(text: $searchText, prompt: "Search tasks")
            .searchScopes($scope) {
                ForEach(SearchScope.allCases, id: \.self) { scope in
                    Text(scope.rawValue).tag(scope)
                }
            }
        }
    }
}
```

`.searchable()` itself only provides the search bar UI and text binding — the actual filtering logic (as shown in `filteredTasks`) is your own responsibility, exactly like `.onDelete`/`.onMove` provide the gesture/UI while leaving the underlying data mutation to your own code.

## 26.12 `.refreshable()` for Pull to Refresh

`.refreshable()` adds the standard pull-to-refresh gesture to a scrollable view, calling your provided `async` closure when triggered and automatically managing the refresh indicator's visibility for the duration of that async work:

```swift
struct TaskListView: View {
    @State private var tasks: [Task] = []

    var body: some View {
        List(tasks) { task in
            Text(task.title)
        }
        .refreshable {
            tasks = await fetchLatestTasks()   // the refresh spinner shows until this async work completes
        }
    }
}
```

Because `.refreshable()`'s closure is `async` (tying directly back to section 17's async/await foundations), you simply `await` your actual data-fetching call inside it — no manual spinner show/hide bookkeeping required, unlike the older UIKit `UIRefreshControl` pattern requiring explicit `beginRefreshing()`/`endRefreshing()` calls.

## 26.13 `ScrollView` and `LazyVStack`

`ScrollView` provides scrolling for arbitrary content (not just row-based lists), and `LazyVStack` (paired with it for large content) creates its children **lazily** — only as they're about to become visible — rather than all upfront the way a plain `VStack` would, which matters significantly for performance with large content sets.

```swift
ScrollView {
    LazyVStack(spacing: 12) {
        ForEach(items) { item in
            ItemRow(item: item)
        }
    }
}

ScrollView(.horizontal) {
    LazyHStack {
        ForEach(items) { item in
            ItemCard(item: item)
        }
    }
}
```

The eager-vs-lazy distinction directly parallels section 3.18's `.lazy` collection sequences: a plain `VStack` inside a `ScrollView` creates and holds *every* child view immediately regardless of visibility, while `LazyVStack`/`LazyHStack` defer creating (and destroying, as they scroll out of view) each row's view hierarchy until it's actually needed on screen — essential for smoothly scrolling through hundreds or thousands of items.

---

## 26.14 `LazyVGrid` and `GridItem` Sizing

`LazyVGrid` arranges content into a grid with a specified column configuration, lazily creating cells just like `LazyVStack` does for rows — `GridItem` describes each column's sizing behavior:

```swift
let columns = [
    GridItem(.flexible()),           // shares available width equally with other .flexible() columns
    GridItem(.flexible()),
    GridItem(.flexible())
]

ScrollView {
    LazyVGrid(columns: columns, spacing: 16) {
        ForEach(items) { item in
            ItemThumbnail(item: item)
        }
    }
}

let adaptiveColumns = [GridItem(.adaptive(minimum: 100))]   // as many columns as fit, each at least 100pt wide

ScrollView {
    LazyVGrid(columns: adaptiveColumns) {
        ForEach(items) { item in
            ItemThumbnail(item: item)
        }
    }
}
```

`.flexible()` columns divide available width equally (like multiple `Spacer`s sharing space); `.adaptive(minimum:)` instead computes however many columns of at least the given width actually fit, which is the standard technique for a responsive photo-grid-style layout that naturally adjusts its column count across different screen widths without any manual size-class branching.

---

## 26.15 `Grid` for Fixed Two-Dimensional Layouts

Unlike `LazyVGrid` (built for large, scrollable, uniformly-structured content), `Grid` is designed for smaller, fixed two-dimensional layouts where rows and columns need genuine alignment across each other — like a form or a small table, where a value in row 2 should align with its label in row 2, and that same column should align across every row.

```swift
Grid(alignment: .leading) {
    GridRow {
        Text("Name:")
        Text("Nahidul")
    }
    GridRow {
        Text("Email:")
        Text("nahid@example.com")
    }
}
```

`Grid` automatically computes consistent column widths across all its `GridRow`s (so the second column always starts at the same horizontal position, regardless of the first column's varying content length in each row) — something `LazyVGrid`'s independent, per-item-sized cells don't provide, since `LazyVGrid` isn't designed around cross-row column alignment the way `Grid` specifically is.

## 26.16 `.scrollPosition()` and Programmatic Scrolling

`.scrollPosition()` lets you both read and programmatically control which item a scroll view is currently positioned at, binding to an item's `id` rather than a raw pixel offset:

```swift
struct ScrollableList: View {
    @State private var scrolledID: Task.ID?

    var body: some View {
        ScrollView {
            LazyVStack {
                ForEach(tasks) { task in
                    TaskRow(task: task)
                        .id(task.id)
                }
            }
        }
        .scrollPosition(id: $scrolledID)

        Button("Scroll to first") {
            withAnimation {
                scrolledID = tasks.first?.id   // programmatically scrolls to that specific item
            }
        }
    }
}
```

Binding to an item's `id` (rather than a raw offset) is deliberately more robust to content changes — if items are inserted, removed, or resized, id-based scroll positioning still correctly targets the intended logical item, whereas a raw pixel offset would become stale and incorrect the moment the content layout shifts.

---

## 26.17 `.scrollTargetBehavior()` and Paging

`.scrollTargetBehavior()` controls where a scroll view "snaps" to when the user stops scrolling — `.paging` snaps to full-view-sized pages (like a classic page-based carousel), while `.viewAligned` snaps to align with individual child view boundaries (commonly paired with `containerRelativeFrame()` from section 24.21 for a "show N items per page, snap between groups" carousel effect).

```swift
ScrollView(.horizontal) {
    LazyHStack {
        ForEach(items) { item in
            ItemCard(item: item)
                .containerRelativeFrame(.horizontal)
        }
    }
    .scrollTargetLayout()
}
.scrollTargetBehavior(.viewAligned)   // snaps to align with each item's boundary as scrolling settles
```

`.scrollTargetLayout()` (applied to the container holding the scrollable content) marks which layout's children should be considered as snap targets — required alongside `.scrollTargetBehavior()` for view-aligned snapping to actually know which child boundaries to snap against.

---

## 26.18 `.onScrollGeometryChange()` 🟠

`.onScrollGeometryChange()` observes a scroll view's geometry (content offset, content size, visible size) changing over time, reporting updates via a callback — directly analogous to `.onGeometryChange()` from section 24.20, but specifically scoped to scroll-related geometry rather than general view size/position.

```swift
struct ScrollTrackingView: View {
    @State private var isScrolledPastTop = false

    var body: some View {
        ScrollView {
            content
        }
        .onScrollGeometryChange(for: Bool.self) { geometry in
            geometry.contentOffset.y > 0
        } action: { wasScrolled, isScrolled in
            isScrolledPastTop = isScrolled
        }
    }
}
```

This is the modern, non-`GeometryReader`-requiring way to build effects that react to scroll position — like a navigation bar that becomes opaque only after the user has scrolled past a certain point — avoiding `GeometryReader`'s greedy-expansion pitfall (recall section 24.19) that would otherwise complicate wrapping an entire scroll view just to observe its offset.

---

## 26.19 `.scrollEdgeEffectStyle()` 🔵

`.scrollEdgeEffectStyle()` controls the visual treatment applied at a scroll view's edges as content scrolls underneath fixed UI elements (like a navigation bar or tab bar) — tying into the Liquid Glass design language (fully covered in section 32) where content can visually blur or fade as it passes beneath translucent system chrome.

```swift
ScrollView {
    content
}
.scrollEdgeEffectStyle(.soft, for: .top)   // a soft blur/fade treatment as content scrolls under the top edge
```

This is a relatively subtle, presentation-layer detail compared to most of this section's more functionally significant topics — it affects how content visually transitions as it scrolls beneath overlapping system chrome, rather than affecting scrolling behavior or data itself.

## 26.20 Reordering in Lists, Grids, and Sections (iOS 27) 🔵

Recent iOS versions extended drag-to-reorder support (previously largely `List`-specific via `onMove`, recall 26.7) to also work naturally within `LazyVGrid`/`Grid` layouts and across `Section` boundaries within a single list — letting users drag an item not just up and down within a flat list, but between distinct sections or grid positions.

```swift
List {
    Section("To Do") {
        ForEach(todoTasks) { task in
            Text(task.title)
        }
        .onMove { /* ... */ }
    }
    Section("Done") {
        ForEach(doneTasks) { task in
            Text(task.title)
        }
        .onMove { /* ... */ }
    }
}
```

This extension makes patterns like a Kanban-style board (dragging a task between "To Do" and "Done" sections) or reordering within a photo grid substantially more natural to implement using SwiftUI's built-in reordering mechanisms, rather than requiring a fully custom drag-and-drop implementation (covered generally in section 57.14's `Transferable` coverage) for these specific, common cross-section/cross-grid reordering scenarios.

## 26.21 List Performance: What Makes Scrolling Stutter 🟠

Scrolling performance problems in `List`/`ScrollView` almost always trace back to expensive work happening synchronously on the main thread during scrolling — heavy computation inside a row's `body`, un-cached image decoding/resizing happening repeatedly, or (most commonly) not using the lazy containers (26.13–26.14) at all and instead eagerly creating every row's entire view hierarchy upfront regardless of visibility.

```swift
// Problematic: expensive work re-computed every single time this row's body evaluates
struct SlowRow: View {
    let task: Task
    var body: some View {
        Text(task.title)
            .background(expensiveColorComputation())   // recomputed on every scroll-triggered re-render
    }
}

// Better: compute expensive values once, outside the frequently-re-evaluated body,
// or cache the result so repeated evaluations don't redo the same expensive work
```

Beyond avoiding expensive per-row computation, using `LazyVStack`/`LazyVGrid`/`List` (rather than eager `VStack`/`Grid`) for large content, ensuring images are appropriately pre-sized/cached rather than decoded fresh on every appearance (recall section 69.12's image decoding cost coverage), and profiling with Instruments' Time Profiler and Animation Hitches tool (both covered fully in section 69) are the standard diagnostic and remediation techniques for tracking down and resolving real-world scrolling stutter.
